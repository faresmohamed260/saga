## Historical scene segmentation design

The prototype first tried classical scene segmentation such as TextTiling and formatting/regex breaks. The project documentation records that these approaches were inconsistent across books and writing styles: they could split dialogue incorrectly or miss subtle time/location/POV shifts.

The replacement "Smart Scene Detection" used an LLM as a semantic supervisor:

1. ask for the first short phrase of each new scene;
2. find those phrases verbatim in the original chapter;
3. sort/deduplicate the exact source indices;
4. slice the original prose at those indices.

The useful design principle is **semantic boundary proposal + deterministic source anchoring**. Phase 3 should preserve that principle while replacing the expensive hosted/full-chapter LLM dependency with measured local methods.

## Historical tension design

Tension was a two-stage process:

1. assign every scene an integer tension value from 1 to 10;
2. aggregate all scene values into a whole-book profile to identify peaks, valleys, overall pacing, and unresolved hooks.

The architecture concept remains useful, but the numeric values were model judgments rather than objective labels. Phase 3 must therefore test consistency and downstream usefulness rather than treating `5.49` as a target.

## Historical causal/event design

The prototype maintained a causal-graph metric layer and surfaced high-consequence/low-resolution "sequel seed" events. The full-book run reported 24 key causal events.

Again, `24` is not a target count. The relevant product properties are:

- extracted events are source-grounded;
- actor/action/object/participants are correct;
- causal links are justified by evidence;
- duplicate events are controlled;
- important consequences and unresolved branches are not systematically missed.

## Why the architecture was replaced

The graduation evaluation explicitly identified the old bottleneck:

- multiple independent LLM requests across scene splitting, style, entities, relationships, tension, and causality;
- request volume grew with book/series size;
- rate limits and timeouts appeared on larger workloads;
- overlapping context was repeatedly retransmitted;
- overall computation and latency were unnecessarily high.

The new Phase-3 local-first architecture must preserve analytical breadth while avoiding that cost pattern.

## How this baseline should be used

For each new scene/event/location/tension candidate stack, report:

- primary-suite book/source fingerprint;
- model/config revision;
- whole-book runtime/RAM/VRAM;
- scene/entity/event/location/tension coverage;
- source-grounded quality metrics from manually verified samples;
- comparison against this historical breadth **without turning these old counts into pass/fail thresholds**.

The preferred outcome is not "135 scenes again." It is a more reliable, reproducible, cheaper narrative model that covers the same product concepts and survives direct inspection on the same modern fantasy books.
